## 1. 现状调研

### 1.1 已有瓦片数据

拿到的是多套 WebODM 正射影像瓦片集，实测特征如下：

| 维度 | 实测结果 |
| --- | --- |
| 目录结构 | `<根目录>/<z>/<x>/<y>.<jpg\|png>`，先列号目录、再行号文件 |
| 编号约定 | 标准 Google/XYZ（北起源），非 TMS 翻转 |
| 瓦片尺寸 | 512 × 512 |
| 图片格式 | 同一批数据里 JPEG 与 PNG 混用 |
| 层级范围 | 覆盖 z1–z22，各层级宽度不等 |
| 总规模 | 十几 GB、几十万个文件量级 |
| 覆盖形状 | 每个数据集都是稀疏覆盖，同一层级内并非矩形满铺 |

实测结论（直接决定解析器写法）：

1. 「先列号目录、再行号文件」是这批数据的实际编排，解析器不能假定 `<z>/<y>/<x>`；
   个别数据集在根目录下还多套了一层同名目录，需要向下探测。
2. 编号是标准 **Google/XYZ（北起源）** 值，不是 TMS 翻转值。
   用瓦片编号反算经纬度后与影像内容对得上，这一点在渲染阶段也得到验证。
3. **每个数据集都是稀疏覆盖**：同一层级内只有实际拍摄区域有图，其余是空洞，
   查看器必须优雅处理缺片。
4. 数据量意味着 **启动时绝不能全量扫描**。最高层级单层就有几十万个文件，
   一次 `ls` 级别遍历要数十秒，必须改成按需列举 + 负缓存。

## 3. 核心算法

### 3.1 投影与坐标换算

- WGS84 经纬度 ↔ Web Mercator 米（正/反算，标准 slippy 公式）
- 经纬度 ↔ 瓦片 `(z, x, y)` ↔ 瓦片内像素 `(px, py)` 三向互转，全程 `Double`，往返误差 < 1e-9
- 视图变换：视口 ↔ 墨卡托的仿射矩阵（缩放 + 平移），所有命中测试走同一套矩阵，保证像素级对齐
- 派生信息：比例尺（1 px 对应实地米数）、当前分辨率、可见瓦片集合

### 3.2 距离测量

- 分段距离用 **Vincenty 反向公式**（WGS84 椭球，毫米级收敛），纯 Swift 实现约 60 行
- 每条边同时给出：长度、正/反方位角、与上一条边的转角
- 总长度、起点到终点直线距离、闭合差
- 拖动预览阶段用**球面 haversine** 快速估算（每帧都要算，省 CPU），松手后切回精密算法

### 3.3 面积与坐标读数

- 多边形面积用测地面积公式（球面过剩 + 纬度带修正），不自建墨卡托平面近似，避免高纬度误差
- 坐标读数同时显示：十进制度、度分秒、Web Mercator 米、当前 `z/x/y` 与瓦片内像素

### 3.4 坐标系基准（关键风险点）

国内常见瓦片来源与基准的对应关系：

| 来源 | 基准 | 与 WGS84 的偏差 |
| --- | --- | --- |
| 天地图 / 自采卫星影像 | CGCS2000 ≈ WGS84 | 可忽略 |
| 高德 / 腾讯 | GCJ-02（火星坐标） | 城区 100–500 m |
| 百度 | BD-09 | 更大 |

若这两个数据集的底图来自高德系，直接按 WGS84 读数会出现几百米偏移，这对测量工具是硬伤。因此设计里把 **基准作为数据集的属性**，提供 WGS84 / GCJ-02 / BD-09 三档切换与互转算法，界面上明确标注当前基准。首次打开数据集时可让用户确认一次，之后记住。

## 4. 渲染与性能

### 4.1 渲染方案

每个可见瓦片对应一个 `CALayer`，`contents` 直接指向解码后的 `CGImage`，位置由统一的仿射变换决定。平移缩放时只改图层 transform，由窗口服务器在 GPU 上合成，**CPU 不参与重绘**。这是 MapKit 与 `CATiledLayer` 的同款思路，在本项目规模下性能充裕。

瓦片在整数层级上取用最接近的一层，跨层时用 `magnificationFilter = .trilinear` 平滑放大；`contentsScale` 跟随屏幕倍率，Retina 上文字与线划不糊。

测量标注层独立于瓦片层，用 `CAShapeLayer` + `CATextLayer` 绘制折线、顶点、边长标签。这样平移时瓦片不动、标注跟着动，互不干扰。

> 后续若装上 Xcode，可在 `TileCanvasView` 后加 Metal 后端做重采样与锐化，不影响现有结构。

### 4.2 数据加载

- **按需列举**：只为正在查看的层级枚举目录，结果缓存；缺失瓦片记入负缓存，避免反复 IO
- **两级缓存**：`NSCache` 按字节数限制内存（默认 512 MB 可调），可选磁盘缓存存解码结果
- **并发**：`actor TileProvider` 管理加载队列，`TaskGroup` 并行解码，优先级为「当前视口 > 视口外一圈预取 > 远景」
- **取消**：视口快速变化时取消已无意义的加载任务，避免抖动
- **索引**：首次打开数据集时后台生成层级索引（各层 bbox、瓦片数、空片比例），用于「缩放到数据范围」与层级切换；UI 不阻塞，进度可显示

### 4.3 目标指标

| 指标 | 目标 |
| --- | --- |
| 平移/缩放帧率 | 60 fps（Apple Silicon） |
| 首次出图 | 打开数据集 < 1.5 s |
| 瓦片命中 | 内存命中 < 1 ms，磁盘命中 < 10 ms |
| 坐标读数延迟 | < 16 ms（跟随鼠标无卡顿） |
| 大目录安全 | z22 级别（41 万片）目录打开不冻结 UI |

## 9. 风险与待确认

1. **坐标系基准**：这两个数据集的底图来源是天地图系还是高德系？直接决定坐标读数是准的还是偏几百米。（默认按 WGS84，界面可切换）
2. **精度要求**：测距是够用就行（米级），还是需要测绘级（结合地方坐标/投影带）？
3. **是否需要 MBTiles / 离线包**：当前是散文件目录。如果以后要支持 `.mbtiles` 单文件，架构已预留，但需要额外开发。
4. **是否要装 Xcode**：不装也能完整开发和交付 `.app`；装了可以做 SwiftUI Preview、Metal 后端和正式签名公证。目前按「不装」推进。
