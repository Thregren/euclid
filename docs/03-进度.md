## M6.1 · 缺陷修复 ✅

两个都是「换层级」引起的渲染问题，靠 `EUCLID_TRACE_VIEW=1` 打出的每帧数字定位：

- **切换缩放层级后瓦片整屏消失**：渲染层维护了一个「请求过就不再请求」的集合，
  而换层级会把不再需要的图层整批移除；回到该层级时图层是新建的、图片却不会再取，
  只剩空的占位图层，整屏看起来就是「瓦片都没了」。
  现在判断依据改为「这一帧还缺图 + 没有在途请求 + 不是已确认缺片」，
  已取过的图片由 `TileProvider` 的内存缓存直接命中，不再有这道永久门槛
- **缩放到上下限后继续滚动会平移视图**：`zoomed(by:anchorViewPoint:)` 先按未夹取的层级
  计算锚点补偿、再 `clamped` 只修正比例尺，于是到达极限后每一格滚动都变成一次平移，
  几步就把影像推出画面（实测每步中心漂移约 1.3e-4 世界单位，而数据集只有 1.8e-4 宽）。
  现在把目标层级先夹到范围内再算补偿，层级不变时直接返回原相机

附带改进：取图队列在有并发额度空出时自动补跑，不再依赖用户继续操作。
自检相应新增 13 项（151 项总计），覆盖缩放极限处的连续缩放与锚点补偿。

## M6.2 · 消除加载与换层级时的闪烁 ✅

用户反馈「加载起来一闪一闪」，用 `EUCLID_TRACE_VIEW=1` + `EUCLID_DEBUG_SNAPSHOT` 逐帧定位到三个原因，
都在「图还没到位的那一瞬间」：

- **渲染空转**：兜底逻辑对「自己没有图、祖先也没有图」的格子每一轮都重新找一遍，
  找不到就再补跑一次同步，形成没有终止条件的回路。打开数据集时相机还停在数据之外，
  整个屏幕都是这种格子，实测同一帧日志刷了 2400 行、每秒两百多轮全量重绘
  （每轮都要重铺图层、重画标注、把 viewport 重新推给 SwiftUI）。
  现在把这类格子记进 `unresolvedTiles`，只在仍留在屏幕上时保留结论，候选集合只减不增，
  回路几轮内收敛：同样的打开流程从 2076 次同步降到 27 次
- **换层级蒙灰**：新瓦片图层原先先刷一层 35% 透明的占位色，而且插在保留的上一层影像**上面**，
  跨层级瞬间整屏像蒙了一层灰白纱（逐帧实测：影像最暗值从 65 被抬到 136，并出现大片 183 的平色），
  等图从磁盘解码完才恢复。现在新图层保持透明、由上一层影像顶着，自己的图到了再淡入；
  同一套缩放脚本下，修复前 4 个换层级帧全部发灰，修复后均为正常影像
- **首次落图硬贴**：瓦片按解码完成的先后上屏，一屏几十块「啪、啪」跳出来；
  现在首次出现也走 120 ms 淡入
- 顺带：数据范围算出来之前不再铺图。此前会停在与数据无关的位置铺一屏空占位并白读磁盘，
  范围一到画面整体跳一次；现在这期间画布保持空白，状态栏显示「正在读取数据范围…」

## M7 · 在线瓦片下载 ✅

按范围与层级把在线瓦片取到本地目录，落成 `<z>/<x>/<y>`，下载完可以直接用本程序打开离线浏览。

- **取图核心（`TileKit/TileSource.swift`、`TileKit/TileDownloader.swift`）**
  - 瓦片源就是一个 URL 模板：支持 `{z}` `{x}` `{y}`，另有 `{-y}`（TMS 行号）、
    `{s}`（子域轮转）、`{key}`（密钥按查询值转义）。因此 XYZ 直连、`{z}/{y}/{x}` 顺序、
    WMTS KVP（把 `TILEMATRIX={z}&TILEROW={y}&TILECOL={x}` 写进模板）都用同一套代码
  - 计划只保存每层的行列范围（不逐个存瓦片），东、南边界取「覆盖到即算」并用 1e-9 瓦片的容差
    吸收归一化坐标往返误差，贴着瓦片分界线的范围不会多取一圈
  - 下载器：并发上限 + 每秒请求数节流，404/410 记为缺片不重试，5xx/429/超时按指数退避重试，
    已存在的瓦片默认跳过，随时可取消；落盘用原子写，完成后写 `source.json` 与 `attribution.txt`
  - 取图通道抽成 `TileFetching` 协议，自检注入假实现，不依赖网络
- **界面（`EuclidApp/TileDownloadModel.swift`、`DownloadSheet.swift`）**
  - 工具栏「下载在线瓦片」/ ⌘⇧D；预设天地图（影像、影像注记、矢量，需要 tk）与 OpenStreetMap，
    另有「自定义模板」；模板带扩展名时自动用它作落盘后缀
  - 区域可来自当前视图 / 数据范围 / 手输经纬度，层级用步进器调节，实时给出预计瓦片数与粗略体积
  - 进度面板显示完成数、速度、预计剩余与已落盘体积；结束后可直接「打开这个数据集」
  - 状态栏在下载期间显示 `下载 x/y`
- **刻意不内置 Google 地图**：其条款不允许把瓦片抓取到服务之外保存，内置预设等于替用户做违规操作；
  需要别的源时可在「自定义模板」里填自己有权使用的源
- 自检新增 54 项（212 项总计）：范围到行列的换算、边界对齐不多取、模板渲染与密钥、缺片/重试/跳过/并发/取消、
  进度单调、落盘清单、以及「下载目录能被嗅探成数据集」

## M11 · 坐标基准对齐（GCJ-02 / BD-09）✅

技术路线里一直挂着这个风险点（§3.4）：国内不少底图不在 WGS84 上，高德 / 腾讯用 GCJ-02
（城区偏 100–500 m）、百度用 BD-09，而 WebODM 的正射影像在 WGS84 上，
两者直接叠加会整体差几百米，配准核对与读数都被带偏。现在把基准当成**数据源的属性**做掉。

- **算法（`TileKit/Datum.swift`）**
  - `Datum` 三档：WGS84 / GCJ-02 / BD-09，提供 `fromWGS84` / `toWGS84` 双向互转
  - 正向是公开流传的多项式拟合（Krasovsky 椭球 + 三角函数扰动），反向用前向公式迭代逼近，
    6 轮即收敛到厘米级；境外坐标不做偏移，与各家实现一致
  - 单测与公开实现逐位对照：WGS84 (116.404, 39.915) → GCJ-02 (116.410244, 39.916404)；
    境外（东京 / 伦敦 / 纽约）恒等；境内偏移量级在百米级且不超过 1 km
- **叠加对齐（`TileLayerStack.datum`）**
  - 取图行列按「把相机中心移回该基准」后算，于是拿到的是该基准网格下的瓦片编号；
    图形再按 `worldOffset` 落位，两者合起来就是「按基准偏移平移」
  - 偏移取视图中心处的线性近似，米制写法同时进日志与界面提示
  - `EUCLID_TRACE_VIEW=1` 的每帧日志会多打一段 `基准偏移=(东 492m, 北 360m)`，便于核对
- **下载也认基准（`TileDownloadPlan`）**：计划里记录基准，范围四个角换算后再取行列，
  落盘清单与 `source.json`、`attribution.txt` 里都写明基准
- **界面**：侧栏「底图」里多一个「坐标基准」选择器（带说明与偏移提示），
  检查器「在线底图」分区显示当前基准与对齐偏移，切换基准时状态栏给出方向与量级
- **顺带修掉一个缺陷**：在线图层的装配签名原先只含「模板 + 密钥」，
  于是只改基准时图层不重装、画面仍是旧偏移；现在签名带上基准
- 自检新增 57 项（269 项总计），覆盖互转可逆性、境外恒等、与公开实现对照、
  世界坐标偏移与米制偏移一致、偏移基准下的下载计划编号

## M12 · 出图与测量性能 ✅

### 性能：测量结果不再每帧重算（`TileKit/Measurement.swift`）

画布每次同步（平移、缩放、换层级、滚轮）都会重铺测量标注，检查器也会在
读数变化时重取每一条测量的结果。而一次求值要走几十次 Vincenty 反向公式，
圆更狠：360 点测地采样 + 周长 + 面积，合计上千次测地运算——
**这些数字只跟顶点有关，跟相机无关**，之前却在每帧重算。

- `MeasurementCalculator.evaluate(kind:points:)` 带缓存，键就是「类型 + 顶点序列」；
  圆的度量另按「圆心 + 半径」存一份，连 360 点采样一起复用
  （原先采样点缓存在标注层里，检查器那条路径每次都要重新采样）
- 缓存容量固定（结果 256 条、圆 64 条，按写入顺序淘汰），量再久也不会无限涨；
  `TileKit` 不绑主线程，所以加了锁，标注图层与检查器从哪边取都安全
- 另开放 `evaluateUncached`（自检用来逐字段对照）与命中数／条目数（自检用来核对行为）
- 实测：自检里 200 点多边形重复求值 200 次，每帧重算 53.4 ms、缓存命中 1.0 ms（约 50 倍）；
  真机跑一遍缩放脚本（3 条示例测量，含一个圆），缓存命中 464 次
- 自检新增 18 项

### 功能：导出当前视图为图片（⌘⇧E / ⌘⇧C）

判读与量测的结果常常要进报告，之前只能自己截屏。现在：

- 画面就是画布本身（含瓦片、测量标注与读数），下方拼一条信息栏：
  数据源、叠加来源与版权、测量条数、中心坐标、层级，以及一条与屏幕同源的比例尺
- 保存面板里可以取消「包含测量标注」导出干净的地图；
  调试用的瓦片网格永远不进成图
- ⌘⇧C 直接把同一张图放进剪贴板
- 合成与 PNG 编码在 `ViewExporter`；画面本身仍由画布离屏渲染
  （`renderMapImage(includingMeasurements:)`，调试快照与出图共用这一条路径）
- 比例尺刻度抽成 `ScaleBarMetric`，屏幕上的浮动比例尺与成图里的那条用同一份算法

### 修复：离屏渲染出来的文字是上下颠倒的

出图时发现所有标注文字都是镜像的。原因是 `CALayer.render(in:)` 在 y 向下的上下文里
会把 `CATextLayer` 的文字画成上下镜像（瓦片那种「画图片」的内容不受影响），
屏幕上的合成路径则一直正常——所以这个毛病只在离屏渲染（导出图片、调试截图）里看得到。
现在出图前给文字图层补一次纵向翻转、出图后立刻还原
（`MeasurementOverlay.withLabelsUprightForOffscreenRender`）。

### 修复：白底影像上每隔一片有一条浅灰细线

出图核对时量到一串等距的 1px 线（每 505 px 一条），取源瓦片边缘对照，
瓦片本身是干净的白——所以不是数据带的边，而是**渲染时的半像素采样渗色**：
缩放比例不是整数倍时，图层边缘会把瓦片外的透明黑混进来，一整片白底上就看成一格格的细线。
修法是每格 frame 向外撑开半个点（`TileLayerStack.tileSeamOverlap`），让相邻瓦片互相盖住这道缝；
瓦片内容是不透明的，重叠看不出来。修完同一张成图里那 3 条线全部消失（逐列扫描确认）。

验证：本地数据集本身用只读 HTTP 服务当在线底图，`EUCLID_DEMO_MEASUREMENT=1` 铺上示例测量，
`EUCLID_DEBUG_EXPORT_VIEW` 写出成图——浅色与深色各一张，核对文字方向、
信息栏内容（数据源名 + 测量条数 + 中心坐标 + 层级）与右下角比例尺。

## M13 · 直接打开单幅影像（GeoTIFF）✅

以一份真实的 `odm_orthophoto.tif`（7502 × 8176、约 115 MB、分块 256 + AdobeDeflate +
Predictor 2、RGBA 8 位、投影坐标、带内建概览）做靶子，目标是「直接读取显示 tiff」。
瓦片数据集要求先把正射影像切成 `<z>/<x>/<y>` 才能看，这一步对很多人就是拦路虎。

### 自己读 TIFF：只读目录，按需解像素

`ImageIO` 能解整张图，但正射影像动辄上亿像素，整张进内存不现实；
更要紧的是它不暴露 GeoTIFF 的地理标签，没有这些就摆不对位置。于是自己写：

- **`TIFF.swift`**：经典 TIFF 与 BigTIFF；IFD 链与 SubIFD（内建概览）；条带（strip）与分块（tile）
  的偏移/长度表；GeoTIFF 标签（`ModelPixelScale` 33550、`ModelTiepoint` 33922、
  `ModelTransformation` 34264、`GeoKeyDirectory` 34735、双精度参数 34736、ASCII 参数 34737）
- **`TIFFDecoder.swift`**：按屏幕需要的区域逐块解压——未压缩 / Deflate / LZW / PackBits / JPEG，
  8 与 16 位，灰度 / RGB / 调色板 / alpha（含预乘），Predictor 2 还原；
  采样时按缩小倍率决定采样点个数（1:1 取单点，缩小时取 2×2 或 3×3 的稀疏箱式滤波），
  因此低倍显示也不必把整幅影像的每个像素摸一遍
- **`GeoTIFF.swift` / `RasterTileSource`**：瓦片请求 → WGS84 范围 → 影像坐标 → 像素矩形 →
  选层级（挑「刚好够这一屏分辨率」的最小一级，内建概览在这里发挥作用）→ 采样进瓦片画布。
  影像边界只覆盖瓦片一部分时，按位置画进画布其余留空，因此边缘不会拉伸错位
- **`Projection.swift`**：经纬度 / Web 墨卡托 / 横轴墨卡托（UTM 南北半球、CGCS2000 三度与六度带、
  西安 80、北京 54，以及文件内自定义 TM 参数）。反算是 Snyder 的级数展开

### 踩到的两个真问题

1. **系统的 `COMPRESSION_ZLIB` 只吃裸 deflate**：TIFF 的 Deflate 是 zlib 包装（RFC 1950），
   丢给 `compression_decode_buffer` 一律返回 0 ——先剥掉 2 字节头与 4 字节 Adler-32 再解，
   剥不动就按裸流试。这行代码不写，ODM 的默认输出一张也读不出来
2. **像素指针活不过闭包**：解码结果交给 `CGDataProvider` 时用的是 `withUnsafeBytes` 里的指针，
   闭包一返回那块内存就可能被复用 ——症状是**整块瓦片时有时无**（读到已释放的内存）。
   改成由 `Data` 支撑的 provider 后彻底消失。这个偶发问题是被自检里的
   「整幅概览平均 alpha 应约 0.63」断言钉住的：参考数据是 0.6336，我的输出在 0 与 1 之间跳

### 验证

- **自检 329 项**：新增的 TIFF 用例全部由 **libtiff** 写出（`Fixtures/TIFF/`，附生成脚本）——
  同一张源图，一条路径走 `ImageIO`、一条走自带解码，逐像素比对；
  四角坐标与 **PROJ 9.7**（`cs2cs -f "%.10f"`）对照到 **1e-8 度（毫米级）**；
  另有 UTM 50N、CGCS2000 三度带、Web 墨卡托的正反算对照
- **真机**：把 `odm_orthophoto.tif` 设为启动打开的文件，跑缩放脚本 + 出图。
  release 下 1:1 取图 25 ms、首屏（9 块）84 ms、整幅概览（940 × 1024）154 ms；
  成图与它自己的无数据区（独立用 ImageMagick 量得整幅 alpha 均值 0.6336，与我的渲染一致）完全吻合；
  出图信息栏的中心坐标与 PROJ 算出的覆盖范围中心逐位一致
- 调试信息也补齐了：`EUCLID_RASTER_TRACE`（世界坐标 → 像素区域 → 选的层级）、
  `EUCLID_TM_TRACE`、`EUCLID_TIFF_TRACE`，以及「拿一个影像文件当参数」的体检模式

## M14 · 从单幅影像生成瓦片 ✅

看完了 GeoTIFF，自然就要能把它交出去：切成一整套 `<z>/<x>/<y>`，既方便分发，也方便本程序离线浏览。

- **核心（`TileKit/TilePyramidExport.swift`）**：复用与浏览**完全相同**的那条取图链路
  （`RasterTileSource` 按区域解压采样），因此切出来的瓦片与直接看 GeoTIFF 是同一份像素，
  不存在第二套重采样实现；计划沿用下载那套「每级只存行列范围」
- 尺寸 **512（默认，本地浏览按设备像素 1:1）** 或 **256（通用地图约定）**；
  格式 **JPEG（质量默认 85）** 或 **PNG**；4 路并发、可取消、已存在默认跳过（中断可续跑）
- 纯无数据区**不写文件**（稀疏影像不被空文件撑大）；JPEG 无 alpha，透明区先合成白底；
  输出目录写 `attribution.txt`
- **面板（⌘⇧T）**：来源影像（默认带当前打开的那幅）、输出目录、层级范围、尺寸、格式、质量、
  实时预计张数与体积、进度与失败计数、完成后可在访达显示或直接打开该数据集
- **健壮性**：单次生成上限 100 万张（超了直接提示，不空转）；面板参数跟随当前影像；
  失败信息带上具体文件路径

验证：自检新增闭环——生成 → 输出目录被 `DatasetLocator` 认出（尺寸与层级都要对）→
把写出的 PNG 读回来与直接渲染**逐字节比对**；JPEG 另比平均通道差（质量 85 实测 1.6/255）。
真机实测一份 6100 万像素的 ODM 影像生成 z18–z21：计划 789 张、写出 532 张
（257 张无数据自动跳过）、0 失败、50.4 MB、4.4 秒。界面核对用**合成影像**（不含真实数据）。

过程中揪出的 bug：**「选 256」原本失效**（渲染仍用影像默认的 512），
是闭环自检里「写出的瓦片应是 64 × 64」这条断言抓出来的。

四件事一起改，都用合成鼠标在真机窗口里跑过一遍（`uidrive`：click / rclick / drag / scroll）：

- **右键结束测量**：画到一半时 `rightMouseDown` 直接收尾，`⌃`+左键同效（`mouseDown` 里先看修饰键）；
